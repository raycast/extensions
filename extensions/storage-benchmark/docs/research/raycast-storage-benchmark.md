# Raycast Store storage-benchmark extension: feasibility notes

_Checked 2026-08-26. Sources are limited to official Raycast documentation and repositories, direct Raycast Support guidance, Node.js documentation, and Apple documentation._

## Implementation update

On 2026-08-26, Raycast Support recommended adding the Swift source directly to the extension and using Raycast's built-in Swift compiler, with the official Color Picker extension as the reference. The implementation now uses [`raycast/extensions-swift-tools`](https://github.com/raycast/extensions-swift-tools): `ray build` compiles the committed Swift package and generates the TypeScript bridge. No precompiled executable, download, checksum, or shell process launch remains in the extension.

The generated bridge returns the final encoded result but does not expose streaming stdout or a child-process handle. The selected transport therefore uses throttled, versioned progress snapshots in a private per-run temporary directory and a cancellation marker checked by Swift between aligned I/O chunks. Native signal handlers retain cleanup when Raycast terminates the compiled process.

## Conclusions

### 1. Native binaries and child processes: yes, with review constraints

A Store extension can execute child processes. Raycast extensions run in a managed Node.js runtime and are not additionally sandboxed for Node file I/O, networking, or other Node features. Raycast's Store guidance explicitly allows calling known system binaries and conditionally allows downloaded or bundled binaries. Bundled binaries must have available, traceable source/build provenance; heavy or opaque binaries are rejected. A downloaded binary must come from a trusted location the author cannot silently replace and must have an integrity check such as a pinned hash. A binary copied from an npm package into assets is acceptable only with traceable build sources, and the guidance currently says to ask Raycast staff to add it. ([Raycast security model](https://developers.raycast.com/information/security), [Store binary guidance](https://developers.raycast.com/basics/prepare-an-extension-for-store#binary-dependencies-and-additional-configuration))

There is direct Store precedent: Raycast's official Speedtest extension downloads Ookla's platform binary, verifies a hard-coded SHA-256, makes it executable, and launches it with `child_process.spawn`. ([download and verification](https://github.com/raycast/extensions/blob/main/extensions/speedtest/src/lib/cli.ts), [process launch](https://github.com/raycast/extensions/blob/main/extensions/speedtest/src/lib/speedtest.ts))

For a disk benchmark, prefer `spawn`/`execFile` with an argument array rather than a shell command. Node documents asynchronous `spawn`, `AbortSignal`, timeouts, and `subprocess.kill()`; synchronous variants block the event loop. ([Node.js `child_process`](https://nodejs.org/api/child_process.html)) Raycast's `useExec` is also available, but its documented default timeout is 10 seconds unless overridden, and Raycast recommends avoiding its shell mode for portability, performance, and command-injection reasons. ([Raycast `useExec`](https://developers.raycast.com/utilities/react-hooks/useexec))

### 2. User-selected folder or mounted volume: yes, subject to macOS access controls

Raycast supports both a runtime directory picker (`Form.FilePicker` with `canChooseDirectories` and `canChooseFiles={false}`) and manifest preferences of type `directory`; both yield filesystem path strings. ([Form file picker](https://developers.raycast.com/api-reference/user-interface/form#formfilepicker), [manifest preferences](https://developers.raycast.com/information/manifest#preference-properties), [Preferences API](https://developers.raycast.com/api-reference/preferences))

The extension can then use Node filesystem APIs on that path because Store extensions are not further sandboxed. Access is nevertheless inherited from the Raycast parent process and remains subject to macOS privacy/TCC and normal filesystem permissions. Raycast specifically notes that protected locations require permission granted to Raycast. Apple lists Desktop, Documents, Downloads, network volumes, and removable volumes under Files & Folders controls, and Full Disk Access covers otherwise protected data. ([Raycast permissions](https://developers.raycast.com/information/security#permissions), [Apple file-access controls](https://support.apple.com/guide/security/secddd1d86a6/web), [Apple Privacy & Security settings](https://support.apple.com/en-ca/guide/mac-help/mchl211c911f/mac))

Therefore a mounted writable volume can be selected by choosing a directory on it, but selection does not guarantee write access. The command should validate that the target is a directory, is writable, and has sufficient free space before creating its test file.

### 3. Long-running progress, cancellation, and preferences

- **Indeterminate progress:** `List`, `Grid`, `Detail`, and `Form` expose `isLoading`; Raycast recommends rendering promptly and using it while work continues. ([UI loading guidance](https://developers.raycast.com/api-reference/user-interface))
- **Background/no-view feedback:** `showToast` with `Toast.Style.Animated` remains visible until completion, can have its title/message/style updated, and supports primary/secondary actions. Raycast explicitly cites cancellation as a toast-action use case; if the Raycast window is closed, a toast falls back to a HUD. ([Toast API](https://developers.raycast.com/api-reference/feedback/toast))
- **Determinate display:** `getProgressIcon(progress)` accepts a value from 0 to 1 and can be rendered wherever Raycast accepts an image, such as a `List.Item`. ([`getProgressIcon`](https://developers.raycast.com/utilities/icons/getprogressicon))
- **Cancellation plumbing:** expose an `Action` and/or toast action that calls an `AbortController` and terminates the spawned benchmark process. `usePromise` accepts an abort-controller ref for cancelling superseded calls, while Node's `spawn` accepts an `AbortSignal` and `ChildProcess.kill()` sends a termination signal. ([Raycast `usePromise`](https://developers.raycast.com/utilities/react-hooks/usepromise), [Node.js `child_process`](https://nodejs.org/api/child_process.html))
- **Preferences:** define extension-wide or command-specific preferences in `package.json`, read them with `getPreferenceValues`, and link users to `openExtensionPreferences` or `openCommandPreferences`. A required preference is collected before the command opens. A `directory` preference is appropriate for a default benchmark target; options such as test size or run count fit dropdown/text/checkbox preferences. ([Preferences API](https://developers.raycast.com/api-reference/preferences), [Store preference guidance](https://developers.raycast.com/basics/prepare-an-extension-for-store#preferences))

No general Raycast-owned task-cancellation primitive was found; cancellation must be wired from Raycast UI actions to the underlying async operation/process.

### 4. Store submission, review, privacy, and open source

- Public Store extensions are open source in the public [`raycast/extensions`](https://github.com/raycast/extensions) repository. Submission uses `npm run publish` to open a GitHub pull request; Raycast reviews it, CI validates/builds it, and merging publishes it automatically. ([publishing](https://developers.raycast.com/basics/publish-an-extension), [security and review](https://developers.raycast.com/information/security#publishing-process))
- The manifest must use the author's Raycast username, an `MIT` license, the latest Raycast API, and the correct platform restriction (this extension should declare macOS if its benchmark/native path is macOS-specific). Use npm and commit `package-lock.json`; run the distribution build and lint before submission. ([Store preparation](https://developers.raycast.com/basics/prepare-an-extension-for-store#metadata-and-configuration))
- Binary provenance, size, trusted download origin, and hash verification are review-critical. Keychain-access requests are rejected. ([binary and Keychain rules](https://developers.raycast.com/basics/prepare-an-extension-for-store#binary-dependencies-and-additional-configuration))
- External analytics are prohibited. Raycast's extension guidelines say collected information may be used only to connect to the relevant service and improve the extension's response; they also require compliance with third-party terms and reject unauthorized scraping/access. ([analytics rule](https://developers.raycast.com/basics/prepare-an-extension-for-store#analytics), [Extensions Guidelines](https://manual.raycast.com/extensions-guidelines))
- For this local benchmark, keep paths/results local unless the user explicitly invokes an export/share action, disclose creation and deletion of temporary test data, and ensure cleanup on success, failure, and cancellation. **This is a privacy/safety recommendation inferred from the rules, not an explicit Raycast disk-benchmark requirement.**

### 5. Cache control and timing: use a small native benchmark helper

Apple documents `F_NOCACHE` as the macOS file-descriptor control that disables data caching and recommends 4 KiB-aligned buffers for uncached reads. The macOS `fcntl(2)` manual likewise defines `F_NOCACHE` as the switch for file data caching. ([Apple File-System Performance Tips](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/FileSystem/Articles/FilePerformance.html), [Apple `fcntl(2)` manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html))

Node exposes `O_DIRECT` only when the host operating system provides it and warns that not every filesystem constant exists on every platform. On the current macOS development host, Node v22.23.2 reports `fs.constants.O_DIRECT` as `undefined`; the installed macOS SDK instead defines `F_NOCACHE`, `F_FULLFSYNC`, and related `fcntl` operations. Standard Node filesystem APIs do not expose a general `fcntl` call. ([Node.js filesystem constants](https://nodejs.org/api/fs.html#file-open-constants))

Node's `performance.now()` is a stable high-resolution clock, so timing itself does not require native code. ([Node.js performance measurement APIs](https://nodejs.org/api/perf_hooks.html#performancenow))

**Engineering inference:** implement measurement in a small, source-available macOS Swift package that opens the test file, applies `F_NOCACHE`, uses appropriately aligned buffers, emits machine-readable progress/results, and owns cleanup. Compile it through Raycast's Swift integration while keeping UI, history, preferences, suite orchestration, and interpretation in TypeScript. A buffered Node-only prototype can be useful as a comparison, but should not be presented as the trustworthy benchmark engine because filesystem cache effects could dominate short tests.

## Not verified / explicit boundaries

- No official source reviewed promises that choosing a directory itself grants Raycast new macOS TCC permission; protected, network, and removable-volume access can still be denied.
- Raw block-device access (for example `/dev/disk*`), unmounted volumes, privileged I/O, cache-purging, or bypassing filesystem semantics was not verified and should be treated as out of scope for a Store extension unless Raycast approves it explicitly.
- No documented maximum foreground-command duration was found. Keep the view/loading state alive, create the cancellation marker during unmount, handle native termination signals, and retain defensive stale-file cleanup.
- No official requirement for a separate extension-specific privacy-policy file was found in the reviewed Store documents. This does **not** remove the obligation to follow Raycast's privacy, analytics, disclosure, and third-party-service rules.

## Follow-up: can the benchmark engine be pure Node.js?

### Verified facts (Apple and Node.js)

- Node's promise-based `FileHandle` API supports positioned/sequential `read` and `write`, exposes the number of bytes actually transferred, and requires callers to await operations on the same file. It also exposes `sync()` (an OS/device-specific request to flush file data and metadata) and `datasync()` (synchronized I/O completion without flushing modified metadata). Node warns that a write can transfer only part of a buffer, so a benchmark must loop until every requested byte is written. ([Node.js filesystem API](https://nodejs.org/api/fs.html))
- `process.hrtime.bigint()` returns high-resolution real time in nanoseconds, relative to an arbitrary origin rather than wall-clock time, and Node identifies interval-performance measurement as its primary use. This is sufficient for throughput timing; nanosecond representation should not be interpreted as guaranteed nanosecond measurement accuracy. ([Node.js process timing](https://nodejs.org/api/process.html#processhrtimebigint))
- On macOS, `fcntl(fd, F_NOCACHE, 1)` disables data caching for that descriptor; Apple recommends 4 KiB-aligned buffers for uncached reads. ([Apple `fcntl(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html), [Apple file-system performance guidance](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/FileSystem/Articles/FilePerformance.html))
- Apple's `fsync(2)` documentation says `fsync` moves host-side modified data and attributes to the drive, but the drive may still buffer or reorder writes, so it is not a strict power-loss durability guarantee. Apple defines `F_FULLFSYNC` as `fsync` plus a request that the drive flush buffered data to permanent storage. ([Apple `fsync(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html), [Apple `fcntl(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fcntl.2.html))
- The documented Node.js filesystem surface exposes `read`, `write`, `sync`, `datasync`, open flags, and the numeric file descriptor, but no `fcntl()` binding or `F_NOCACHE`/`F_FULLFSYNC` operation. Consequently, pure documented Node.js/TypeScript cannot request those macOS-specific controls directly. ([Node.js filesystem API](https://nodejs.org/api/fs.html))

### Engineering inference and recommendation

**Inference:** a pure Node.js engine can produce a credible **application-level buffered sequential filesystem benchmark**. It can time awaited, sequential, partial-write-safe I/O with `hrtime.bigint()`, report the write loop separately from `FileHandle.sync()` latency, close/reopen the file, and read it sequentially. It cannot credibly claim guaranteed cold-cache, uncached physical-media, or power-loss-durable throughput: the read may be served partly or wholly from the unified filesystem cache, and Node's `sync()` reaches macOS `fsync` semantics rather than Apple's stronger `F_FULLFSYNC` request. Using a fresh file or a data set larger than memory may reduce cache distortion but does not control or prove cache state.

**Smallest technically defensible architecture for Storage Benchmark:** keep orchestration, UI, cancellation, validation, and cleanup in TypeScript, but use one small, open-source Swift package for the timed I/O loop and let Raycast compile it. The native benchmark should create one test file in the selected directory, use `F_NOCACHE`, use aligned reusable buffers, retry partial transfers, publish progress/results through a narrow versioned bridge, and handle termination cleanly. Report (1) uncached sequential write/read throughput and (2) synchronization latency as separate metrics; make `F_FULLFSYNC` an explicitly labelled durability test rather than folding it into nominal throughput. Node's monotonic timer is already adequate, but timing inside Swift minimizes IPC/scheduling boundaries.

If avoiding a native helper is a hard requirement, retain the pure Node engine but name the results **Buffered Filesystem Write**, **`fsync`-Inclusive Write**, and **Filesystem Read (Cache May Apply)**. That narrower claim is technically defensible; calling those numbers raw disk speed is not.
