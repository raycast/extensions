Why it's built this way: the four design decisions

Before any code makes sense, you need the reasoning. Every line in this repo serves one of these:

1️⃣The "database" is a human-readable fileDecision

A normal app would use SQLite or a cloud service. Here, one Markdown file is the database. Why? Because you already live in Obsidian. Your watchlist sits next to your notes, is version-controlled by Git if you want, is readable on any device, and will never die when an API shuts down. The cost: the code must parse and edit Markdown text precisely, with no database engine to help. That cost is exactly what media-data.ts (the biggest file) pays.

2️⃣Zero backend, zero API keyDecision

Metadata comes from Cinemeta, Stremio's public catalog mirror of IMDb data. No account, no key, no rate-limit management. The trade-off: it's a third-party free service, so the code treats every request as best-effort: timeouts, per-request .catch(), and graceful degradation everywhere (a missing plot must never break the list).

3️⃣Views never touch the file; the engine never touches the UIDecision

media-data.ts imports zero React/Raycast modules. Only Node's fs. The React files import zero fs code directly; they only call the engine's seven public functions. This is the classic separation of concerns: you could swap Raycast for a plain CLI tomorrow and reuse media-data.ts untouched, or swap the Markdown file for SQLite and only rewrite that one file.

4️⃣Read → mutate in memory → write whole fileDecision

Every write operation follows the same shape: readLines() loads the entire file into an array of strings, an index-based splice mutates that array, writeLines() writes the whole array back. No partial writes, no append-only log, no file locking. For a single-user file edited a few times a day this is the simplest correct design, and the section-scanning logic guarantees the rest of your note (intros, other headings, journal text) is never touched.

02 · Foundations

Every technology in the stack, from first principles

You said you want to understand everything from all the technologies in this extension. So before we read a single line of project code, here is each technology on its own terms: what problem it exists to solve, and the specific parts of it this codebase uses.

2.1. Raycast: the host application

What Raycast is: a native macOS app (Swift, AppKit) that opens as a floating command window (default hotkey ⌥Space). It is a launcher, like Spotlight, but extensible. The key fact: you never write UI code for macOS itself. You declare UI as React components, and Raycast translates them into real native AppKit views.

How your code runs: when you trigger a command, Raycast spins up a Node.js process (bun, a fast JavaScript runtime), bundles your src/*.tsx, and executes the exported React component. Your React tree is not rendered to a browser DOM. There is no DOM. Raycast provides a custom React renderer: when you write <List />, the reconciler turns it into instructions like "show a native scroll list with these rows", sent over IPC to the Swift app.

🧠

Mental model: you write React as a declarative description; Raycast owns the pixels. That's why there's no CSS anywhere in this repo: you get native macOS look-and-feel for free, and styling options are limited to what the API exposes (colors, icons, tags).

2.2. TypeScript: JavaScript with a compile-time contract

JavaScript's values are dynamically typed: x can be a number now and a string later. TypeScript adds a type layer that is checked before the code ever runs. Your types are erased at build time; what executes is plain JavaScript. The value is purely in the guarantees:

  • Autocomplete & refactoring safety. The editor knows a MediaItem has exactly 11 fields; rename one and every usage is flagged.
  • Contract enforcement. A function declared to return MediaItem[] cannot accidentally return null.
  • Self-documentation. The MediaItem interface is the schema of the Markdown table, written once, enforced everywhere.

2.3. React: the UI as a function of state

The core idea: you don't write "change this label's text" commands. You write a component, a function from state to UI description. When state changes, React calls your function again, compares the new description with the old one (reconciliation), and applies only the difference. In Raycast, the "difference" becomes IPC messages to the native app.

The four hooks this project uses

useState(v)

Returns [value, setValue]. Calling setValue schedules a re-render with the new value. Every piece of changing data in the views lives in one of these: lists, loading flags, search text, the description cache.

useEffect(fn, deps)

"Run fn after render whenever any of deps changed." Used for: loading the file on mount, reacting to search text, fetching descriptions. The optional return value is a cleanup function run before the next effect or unmount.

useCallback(fn, [])

Returns a memoized function: the same function identity across renders unless deps change. Here it makes refresh stable so the mount effect [refresh] runs exactly once instead of every render.

useRef(0)

A mutable box that survives renders without triggering them. Perfect for the request sequence counter in add-media: it's coordination data, not display data. Changing it must NOT re-render.

🔥

The one React trap this codebase carefully avoids (twice): async work inside useEffect can complete after the component has moved on, writing to state of a view that's gone, or an older effect's result overwriting a newer one. The fixes are the cancelled flag (media.tsx:91,109) and the seq.current === mine guard (add-media.tsx:33,38). Both dissected in their sections below.

2.4. Node.js and the fs module: how the file is actually touched

Raycast extensions run in a Node-like runtime, which means full access to the file system, something browser JavaScript never has. This extension uses exactly three functions from fs:

FunctionBehaviorUsed for
existsSync(path)Returns true/false; never throwsGuard before reading, so the user gets "Not found" instead of a crash (media-data.ts:203)
readFileSync(path, "utf-8")Blocks until the whole file is read, returns its full text as a stringEvery operation starts here; then .split("\n") turns it into a line array
writeFileSync(path, text, "utf-8")Blocks while replacing the entire file with the given textEvery mutation ends here; lines.join("\n") turns the array back into text

Why the Sync variants when Node culture says "always async"? Because Raycast commands are short-lived processes doing one small file (a few KB). Blocking for a microsecond is irrelevant, and synchronous code is dramatically easier to reason about: addItem either completes the whole read-check-splice-write sequence or throws. No interleaving, no callbacks, no partial states.

ℹ️

The whole persistence pattern in one line of thinking: text file → split("\n") → array of lines → find index → splice the array → join("\n") → write back. The array-in-the-middle is where all the logic lives; the file is just its serialized form.

2.5. Markdown & Obsidian: the syntax you must be able to read fluently

The "database rows" are Markdown tables. To follow the parser code you need this syntax down cold. A table is always three kinds of lines: 

| ✓ | Poster | Title | … |          ← header row: column names, one line
|:-:|:-:|---| … |              ← delimiter row: alignment per column (:-: center, --- left)
| ☑ | ![|55](https://…) | [Dune](https://…) | … |   ← data row: one movie
  • Alignment row |:-:| means "center this column". Cosmetic in Obsidian, but the parser must recognize the line to skip it (isDivider, media-data.ts:64-67).
  • Image syntax ![alt|55](url) is Obsidian's extension: the |55 in the "alt" slot sets width to 55px. That's why the poster cell is written ![\|55](url), with the pipe escaped even here.
  • Link syntax [Dune](https://www.imdb.com/title/tt1160419/), a clickable title. The IMDb ID is deliberately encoded in this URL so it can be recovered by regex later.
  • Escaped pipe \|: the reason splitRow exists. A literal | inside a cell would split the cell; Markdown's answer is backslash-escaping.
  • Checkboxes ☑ / ☐, not real Markdown checkboxes, just Unicode glyphs in a column. Works fine as long as the parser checks "does cell 0 contain ☑".
  • Headings ## Watchlist, the section markers the engine scans for.
  • Obsidian URI obsidian://open?path=…, a custom URL scheme the Obsidian app registers with macOS; open()ing it jumps straight to the note.

2.6. HTTP, fetch, Promises, and AbortController

HTTP in 20 seconds: the client opens a connection, sends a request line (GET /catalog/movie/top/search=dune.json HTTP/1.1), the server sends back a status code (200 = OK) and a body (here: JSON text). fetch(url) wraps all of that into a Promise, an object representing a value that will arrive later. await pauses the current async function (never the whole process) until the promise settles.

Promise combinators used here: Promise.all([p1, p2]) starts both promises concurrently and resolves when both finish; here it searches the Movies and Series catalogs at the same time, halving latency. Attach .catch(() => []) to each promise individually and a failure of one catalog degrades to "no results from it" rather than killing the whole search.

⏱️

Why AbortController is non-negotiable: fetch has no built-in timeout. On a flaky connection a request can hang for the OS-level TCP timeout, minutes. The pattern: create a controller, arm setTimeout(() => ctrl.abort(), 12000), pass ctrl.signal to fetch, and clearTimeout in finally so a fast success doesn't leave a zombie timer alive. Abort rejects the promise, which the callers turn into either an empty result or a toast.

Cinemeta specifics: the base URL is https://v3-cinemeta.strem.io. Two endpoint shapes matter: /catalog/{movie|series}/top/search={query}.json (search) and /meta/{movie|series}/{imdbId}.json (full detail). Responses are loosely typed JSON, which is why every field passes through asStr/asList guards before touching our types.

4.4. Table primitives: recognizing and building structural lines

function headerLine(): string  { return "| " + COLUMNS.join(" | ") + " |"; }

function isDivider(line: string): boolean {
  const t = line.trim();
  return t.startsWith("|") && /^[\s|:-]+$/.test(t) && t.includes("-");
}
function isTableRow(line: string): boolean {
  return line.trim().startsWith("|") && !isDivider(line);
}

headerLine() and dividerLine() are pure serializers, the inverse of parsing. isDivider comes down to one line: a divider is a line that starts with a pipe, consists only of whitespace/pipes/colons/dashes, and contains at least one dash. That last clause matters: without it, an empty row | | | | would also match. isTableRow then becomes "looks like a table line but isn't the divider", which is exactly how the layout scanner distinguishes header, divider, and data rows while walking the file.

4.5. splitRow(): the escape-aware tokenizer

The single most important function in the engine. Markdown cells are pipe-delimited, but cell content may legally contain an escaped pipe (\|; think of a note like "Great film \| would watch again", or the poster cell which itself contains ![\|55](…)). A naive line.split("|") shreds those rows into extra columns and shifts every field after it, silently corrupting data. So we need a tiny state machine: 

function splitRow(line: string): string[] {
  let s = line.trim();
  if (s.startsWith("|")) s = s.slice(1);      // strip leading pipe
  if (s.endsWith("|"))   s = s.slice(0, -1); // strip trailing pipe
  const cells: string[] = [];
  let cur = "";                              // current cell being accumulated
  for (let i = 0; i < s.length; i++) {
    if (s[i] === "\\" && s[i + 1] === "|") {
      cur += "\\|";                        // escaped pipe: keep as-is …
      i++;                                   // …and skip the next char (the pipe)
    } else if (s[i] === "|") {
      cells.push(cur.trim());                 // real delimiter: cell complete
      cur = "";
    } else {
      cur += s[i];                            // ordinary char: accumulate
    }
  }
  cells.push(cur.trim());                           // last cell has no trailing delimiter
  return cells;
}

Walk it character-by-character on | a \| b | c |: strip outer pipes → scan a … hit \, peek ahead, next is | → append \| to the current cell and jump the loop index past the pipe so it can never be mistaken for a delimiter … hit the real | → emit cell "a \| b" … accumulate c … final push. The peek-ahead-and-skip (i++ inside the branch) does all the work. It's the classic lexer pattern you'd use for quoted strings in any tokenizer.

4.6. esc() / unesc(): the write-side counterpart

function esc(v: string): string {
  return (v || "").replace(/\|/g, "\\|").replace(/\n+/g, " ").trim();
}
function unesc(v: string): string {
  return (v || "").replace(/\\\|/g, "|").trim();
}

Symmetry is the point: esc is applied to every plain value on its way into a cell (pipes become \|, and newlines are flattened to spaces, since a newline would physically break the one-line-per-row invariant); unesc reverses it on the way out. Note (v || ""): a null/undefined sneaking in degrades to empty string instead of throwing. Cheap, total, safe.

4.7. Cell codecs: where Title and Poster hide structured data

Two columns are not plain text. The Title cell is a Markdown link whose URL embeds the IMDb ID; the Poster cell is an image tag whose alt-text encodes a width. The codecs: 

function posterCell(url: string): string {
  if (!url) return "";
  return `![\\|${POSTER_W}](${url})`;   // → ![\|55](https://…)
}
function parsePoster(cell: string): string {
  const m = cell.match(/!\[[^\]]*\]\(([^)]+)\)/);  // alt = anything but ], url = anything but )
  return m ? m[1].trim() : "";
}

function titleCell(title: string, imdbId: string): string {
  const t = esc(title);
  if (!imdbId) return t;                       // manually-added items have no link
  return `[${t}](https://www.imdb.com/title/${imdbId}/)`;
}
function parseTitle(cell: string): { title: string; imdbId: string } {
  const m = cell.match(/^\[(.+?)\]\((https?:\/\/[^)]*?\/title\/(tt\d+)\/?)\)$/);
  if (m) return { title: unesc(m[1]), imdbId: m[3] };
  return { title: unesc(cell), imdbId: ""; };          // fall back: plain text
}

Anatomy of the title regex

FragmentMeans
^\[(.+?)\]starts with [, captures the link text lazily (shortest match, so a ] inside the title doesn't end it early)
\((https?:\/\/[^)]*?\/title\/…)\)the URL in parens, must be http(s)
\/title\/(tt\d+)\/?must contain /title/ followed by the IMDb ID: literal tt + digits; the trailing /? tolerates a trailing slash
$nothing after the closing paren: the whole cell is the link

The graceful fallback is the design point: any cell that doesn't match (hand-typed title, weird edit) still yields a usable title with an empty imdbId, and the rest of the app simply hides IMDb-dependent features for that row. Parsing never throws on user data.

4.8. rowToLine() / lineToRow(): the serializer round-trip

function rowToLine(it: MediaItem): string {
  const cells = [
    it.watched ? CHECKED : UNCHECKED,     // ☑ or ☐, boolean → glyph
    posterCell(it.poster),            // url → ![\|55](url)
    titleCell(it.title, it.imdbId),     // title+id → [title](imdb-url)
    it.kind,                              // "Movie" | "Series" verbatim
    esc(it.year), esc(it.director), esc(it.genre),
    esc(it.imdbRating), esc(it.myRating), esc(it.notes),
  ];
  return "| " + cells.join(" | ") + " |";
}

function lineToRow(line: string): MediaItem {
  const c = splitRow(line);
  const { title, imdbId } = parseTitle(c[2] ?? "");
  const kindRaw = (c[3] ?? "").toLowerCase();
  return {
    watched: (c[0] ?? "").includes(CHECKED),   // glyph → boolean
    poster: parsePoster(c[1] ?? ""),
    title, imdbId,
    kind: kindRaw.startsWith("s") ? "Series" : "Movie", // case-insensitive, default Movie
    year: unesc(c[4] ?? ""), director: unesc(c[5] ?? ""),
    genre: unesc(c[6] ?? ""), imdbRating: unesc(c[7] ?? ""),
    myRating: unesc(c[8] ?? ""), notes: unesc(c[9] ?? ""),
  };
}

These two are pure inverses: lineToRow(rowToLine(item)) equals item for any input. That property is what makes the whole engine trustworthy: you can round-trip the file through the app forever without data drift. Index positions (c[2] = Title) are pinned by COLUMNS; every index lookup is ?? ""-guarded so a truncated row degrades to blanks instead of undefined.

4.9. Section layout: finding rows by scanning headings

The file is an Obsidian note that may contain anything else; the tables live inside it. The engine therefore locates regions before touching anything: sectionBounds finds the span of lines under a ## heading, and layoutOf classifies the lines inside that span. 

function sectionBounds(lines: string[], heading: Section): [number, number] {
  let start = -1;
  for (let i = 0; i < lines.length; i++) {
    const t = lines[i].trim();
    if (t.startsWith("## ") && t.toLowerCase().includes(heading.toLowerCase())) {
      start = i + 1;             // data begins on the line AFTER the heading
      break;
    }
  }
  if (start === -1) throw new Error(`'## ${heading}' section missing from Movies.md`);

  let end = lines.length;              // default: section runs to EOF
  for (let j = start; j < lines.length; j++) {
    if (lines[j].startsWith("## ")) { end = j; break; }  // …or stops at the NEXT heading
  }
  return [start, end];                 // half-open range: [start, end)
}

interface Layout { contentStart: number; hasHeader: boolean; dataStart: number; dataEnd: number; }

function layoutOf(lines: string[], start: number, end: number): Layout {
  let contentStart = start;
  while (contentStart < end && lines[contentStart].trim() === "") contentStart++;  // skip blank lines
  const hasHeader =
    contentStart < end && isTableRow(lines[contentStart]) &&          // a table-ish line…
    contentStart + 1 < end && isDivider(lines[contentStart + 1]); // …immediately followed by the divider
  const dataStart = hasHeader ? contentStart + 2 : contentStart;          // data begins after header+divider
  let dataEnd = dataStart;
  while (dataEnd < end && isTableRow(lines[dataEnd])) dataEnd++;            // …and runs until a non-table line
  return { contentStart, hasHeader, dataStart, dataEnd };
}

Key subtleties: matching on "## " (with trailing space) so a ## Watchlist 2024 heading still matches via the includes-check, while ### sub-headings do not (they'd fail startsWith("## ")… actually a ### also starts with ##, but not with "## ", since the third # isn't a space. Precise string details matter here). The range is half-open [start, end), so end is exclusive. That's the convention that makes splice(dataEnd, 0, row) insert exactly after the last data row. hasHeader: false handles the empty-section case: when you add the first movie ever, the header + divider + row get created together.

4.11. The three internal operations everything is built from

function rowsIn(lines, section): MediaItem[] {          // READ: all rows of a section
  const [s, e] = sectionBounds(lines, section);
  const { dataStart, dataEnd } = layoutOf(lines, s, e);
  const out: MediaItem[] = [];
  for (let k = dataStart; k < dataEnd; k++) out.push(lineToRow(lines[k]));
  return out;
}

function findRow(lines, section, title): { idx: number; row: MediaItem } | null {  // LOCATE: by title
  const [s, e] = sectionBounds(lines, section);
  const { dataStart, dataEnd } = layoutOf(lines, s, e);
  for (let k = dataStart; k < dataEnd; k++) {
    const row = lineToRow(lines[k]);
    if (row.title.toLowerCase() === title.toLowerCase()) return { idx: k, row };
  }
  return null;                                // null, not -1: caller checks truthiness
}

function insertRow(lines, section, it): void {           // INSERT: append at dataEnd
  const [s, e] = sectionBounds(lines, section);
  const lay = layoutOf(lines, s, e);
  if (!lay.hasHeader) {
    lines.splice(lay.contentStart, 0, headerLine(), dividerLine(), rowToLine(it), "");
  } else {
    lines.splice(lay.dataEnd, 0, rowToLine(it));   // 0 deletions → pure insert
  }
}

With read (rowsIn), locate (findRow: case-insensitive title match, returning both the line index and the parsed row), and insert (insertRow appends at dataEnd, creating header+divider if the section was empty), every higher-level operation is a three-line composition: remove = splice(idx, 1), update = lines[idx] = rowToLine({...row, ...patch}), move = remove + insert.

5.2. getJson(): the only fetch in the codebase

async function getJson(url: string, timeoutMs = 12000): Promise<unknown> {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), timeoutMs);
  try {
    const res = await fetch(url, { signal: ctrl.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);   // 404/500 → normal exception
    return await res.json();
  } finally {
    clearTimeout(timer);                        // runs on success AND failure
  }
}

Every network call in the extension goes through these 10 lines. The return type is deliberately unknown, "some JSON", deliberately not any, forcing callers to decode before use (see the asStr guards). finally guarantees the timer is cleared on every path; otherwise a dozen fast successes would leave a dozen pending timers that each fire an abort on an already-finished request.

5.3. The defensive decoders

function asList(v: unknown): string {              // ["Drama","Sci-Fi"] → "Drama, Sci-Fi"
  if (Array.isArray(v)) return v.filter(Boolean).join(", ");
  return typeof v === "string" ? v : "";         // sometimes it's already a string
}
function asStr(v: unknown): string {
  if (v === null || v === undefined) return "";
  return String(v);
}
function firstYear(v: unknown): string {           // "2022–" (ongoing series) → "2022"
  const m = asStr(v).match(/\d{4}/});
  return m ? m[0] : "";
}

Real-world API data is messy: genres arrive as arrays, cast lists sometimes as pre-joined strings, years as "2022–" for running shows, fields sometimes just missing. These three tiny functions are the border checkpoint: nothing leaves cinemeta.ts unless it's a plain string. This is boundary discipline (§2.2) in its purest form.

5.4. search(): one catalog query

export async function search(query: string, kind: MediaKind): Promise<SearchHit[]> {
  const q = query.trim();
  if (!q) return [];                                   // never fetch for empty input
  const url = `${BASE}/catalog/${typePath(kind)}/top/search=${encodeURIComponent(q)}.json`;
  const data = (await getJson(url)) as { metas?: Record<string, unknown>[] };
  const metas = data?.metas ?? [];                       // optional chaining + default
  return metas
    .filter((m) => asStr(m.id).startsWith("tt"))        // IMDb items only
    .map((m) => ({ imdbId: asStr(m.id), name: asStr(m.name),
                year: firstYear(m.releaseInfo ?? m.year), poster: asStr(m.poster),
                kind, genres: asList(m.genres), imdbRating: asStr(m.imdbRating ?? "") }));
}

The URL anatomy: encodeURIComponent makes spaces and & safe inside the URL. mandatory for multi-word queries like "Eternal Sunshine of the Spotless Mind". The filter drops non-IMDb ids (Cinemeta also indexes some other catalogs), and releaseInfo ?? year shows the API being inconsistent between endpoints. Handle both, assume nothing.

5.5. detail(): one full-metadata fetch

export async function detail(imdbId: string, kind: MediaKind): Promise<FullMeta | null> {
  const url = `${BASE}/meta/${typePath(kind)}/${imdbId}.json`;
  try {
    const data = (await getJson(url)) as { meta?: Record<string, unknown> };
    const m = data?.meta;
    if (!m) return null;                                  // valid JSON, no meta → null
    return { imdbId, kind, name: asStr(m.name), … };      // decode every field
  } catch {
    return null;                                           // network/timeout error → null, not throw
  }
}

The signature choice Promise<FullMeta | null> instead of throwing is deliberate: a missing plot is a normal outcome, not an exceptional one. Callers do full?.director || "" and move on. Contrast with getJson, where a timeout should abort aggressively.

5.6. searchAll(): parallel fan-out with per-branch failure

export async function searchAll(query: string): Promise<SearchHit[]> {
  const [movies, series] = await Promise.all([
    search(query, "Movie").catch(() => [] as SearchHit[]),   // failure ≠ total failure
    search(query, "Series").catch(() => [] as SearchHit[]),
  ]);
  return [...movies, ...series];                            // deterministic order: movies first
}

Both requests fly simultaneously (total latency ≈ the slower one, not the sum), and because each has its own .catch, a Series-catalog hiccup yields "movies only" instead of an error screen. The spread order guarantees stable section ordering in the UI.

6.4. The description-fetch effect: the trickiest 20 lines in the repo

useEffect(() => {

    const entries = await Promise.all(
      all.slice(0, 20).map(async (i) => {       // batches of 20
        const m = await detail(i.imdbId, i.kind);
        const bits = [
          m?.description ? m.description : "",
          m?.director    ? `**Director:** ${m.director}` : "",
          m?.cast        ? `**Cast:** ${m.cast}`        : "",
          m?.runtime     ? `**Runtime:** ${m.runtime}`   : "",
        ].filter(Boolean);
        return [i.imdbId, bits.join("\n\n")] as const;   // [k, v] tuple
      }),
    );
    if (!cancelled) setDescs((p) => ({ ...p, ...Object.fromEntries(entries) }));
  })();
  return () => { cancelled = true; };              // cleanup before re-run/unmount
}, [watchlist, watched, descs]);

Four mechanisms interact; each exists because the others aren't enough:

1

Why descs is a dependency at all

When the fetch completes and setDescs runs, descs changes → effect re-runs → the filter now excludes everything just fetched → if anything else was beyond the 20-item batch, it gets its turn. The effect re-arming itself is how the "next batch" gets scheduled.

2

Why it doesn't loop forever

Once the last batch lands in descs, the filter produces an empty array and the guard if (all.length === 0) return exits before any fetch. Steady state: effect runs, does nothing, stops.

3

Why cancelled exists

Between the await starting and finishing, the user may leave the view (Raycast closed it). Writing state to an unmounted component is the classic async bug. The flag is flipped by the cleanup function, and the write is skipped. It also prevents an older in-flight batch from clobbering a newer one.

4

Why as const and fromEntries

[id, text] would infer string[]; as const narrows it to the tuple readonly [string, string]: the exact input type Object.fromEntries expects to build the dictionary merged into the cache via functional setDescs(prev => ({...prev, ...})).

useEffect(() => {

    } catch (e) {

Three mechanisms work together; each is useless without the others:

D

Debounce (the setTimeout + clearTimeout cleanup)

Typing "severance" fires the effect 9 times, but each run's cleanup cancels the previous timer. Only when the user pauses for 320ms does a request actually fire. One network call instead of nine.

S

Sequence guard (mine === seq.current)

Debouncing does not stop this: "dune" fires at t=320ms and resolves slowly at t=900ms, while "dune 2" fires at t=700ms and resolves fast at t=850ms. Without the guard, the stale "dune" results overwrite "dune 2" at t=900ms, results that don't match the search bar. Every state write in the callback is gated on still being the latest request.

N

Noise guard (length < 2)

One-character queries return garbage and burn requests. Below two characters: clear results, stop loading, done.

⚡I/O: synchronous fs vs async fsheresy, justified

Node convention says "never block the event loop." Here blocking is correct: the file is a few KB (reads take ~1ms), operations are user-triggered (not a hot server path), and sync code gives the simplest possible error model: the function either completes the full read-check-mutate-write sequence or throws one catchable error. With async fs you'd need queues or locks to prevent two overlapping operations from interleaving read→write cycles and losing data. Sync is the lock. The moment this becomes a problem (huge files, background refresh), the fix is localized to readLines/writeLines.

✍️Write strategy: full rewrite vs append vs in-place editcorrectness first

Every mutation rewrites the whole file. In-place byte edits (like a database page write) would be faster but require the new row to be exactly the old row's length, absurd for text. An append-only journal (insert events, compact later) is how real databases work, and brings real databases' complexity: compaction, crash recovery, replay. For a file you edit a few times a day, writeFileSync of ~50 lines is instant and trivially verifiable: after any operation, the file is either the old text or the new text, never half of each.

🔑Identity: title-as-key vs IMDb-id-as-keytrade-off accepted

Rows are looked up by case-insensitive title, not IMDb id, because manual entries have no id, and findRow returning null for them would break the duplicate check and every edit. The cost: rename a title and the old key is gone, which is exactly why edit.tsx passes item.title (the pre-edit title) as the lookup key and the new title only inside the patch. A production version would key by id with a fallback to title.

🔁State: file-as-truth vs file-as-cachethe React decision

The views hold no persistent model. After every mutation they call refresh(), which re-reads the file from disk. An alternative, patching React state in place ("optimistic updates"), would be snappier but creates two sources of truth and a classic bug family: state says the row moved, disk says it didn't (write failed), and no one reconciles. Here the disk cannot disagree with the UI for more than one refresh cycle, because the UI is a pure function of the disk. The ~1ms cost of re-reading buys total immunity to cache-invalidation bugs.

🚢What a production version would changehonest gaps
  • Note path via preferences. NOTE_PATH is hard-coded; ship-blocking for the store.
  • Schema version header. A <!-- schema:2 --> line would let future column migrations detect old files.
  • Round-trip tests. lineToRow(rowToLine(x)) === x for nasty inputs (pipes, emoji, empty cells) is a 20-line test that would lock in the parser forever.
  • File watching. Edits made in Obsidian appear only after an in-app action; a debounced fs.watch would close the loop.
  • Optimistic UI on the rating form. The one place a user would feel the refresh; even then, keep file-as-truth underneath.

/** Split a markdown row, honouring \| escapes. */
function splitRow(line: string): string[] {
  let s = line.trim();
  if (s.startsWith("|")) s = s.slice(1);
  if (s.endsWith("|")) s = s.slice(0, -1);
  const cells: string[] = [];
  let cur = "";
  for (let i = 0; i < s.length; i++) {
    if (s[i] === "\\" && s[i + 1] === "|") {
      cur += "\\|";
      i++;
    } else if (s[i] === "|") {
      cells.push(cur.trim());
      cur = "";
    } else {
      cur += s[i];
    }
  }
  cells.push(cur.trim());
  return cells;
}

/** Escape a plain value for safe use inside a table cell. */
function esc(v: string): string {
  return (v || "").replace(/\|/g, "\\|").replace(/\n+/g, " ").trim();
}
function unesc(v: string): string {
  return (v || "").replace(/\\\|/g, "|").trim();
}

L74–76 Trim, then strip the outer pipes, the delimiters of first and last cells, so the loop sees pure cell content.

L80–84 The heart: if this char is \ and the NEXT is |, keep both and i++ to jump past the pipe, so it can never be mistaken for a delimiter. That peek-and-skip is the whole state machine.

L85–89 A real delimiter: emit the accumulated cell (trimmed), reset.

L92 The last cell has no trailing pipe, so push it after the loop.

L95–97 Write-side escape: pipes become \|, newlines become spaces (a newline would physically split one row into two lines), nullish input degrades to "".

L98–100 Read-side inverse. Together with splitRow they guarantee the round-trip property: what goes in comes back out, byte for byte.

/* ---------- section / layout ---------- */

function sectionBounds(lines: string[], heading: Section): [number, number] {
  let start = -1;
  for (let i = 0; i < lines.length; i++) {
    const t = lines[i].trim();
    if (t.startsWith("## ") && t.toLowerCase().includes(heading.toLowerCase())) {
      start = i + 1;
      break;
    }
  }
  if (start === -1) throw new Error(`'## ${heading}' section missing from Movies.md`);
  let end = lines.length;
  for (let j = start; j < lines.length; j++) {
    if (lines[j].startsWith("## ")) {
      end = j;
      break;
    }
  }
  return [start, end];
}

interface Layout {
  contentStart: number;
  hasHeader: boolean;
  dataStart: number;
  dataEnd: number;
}

function layoutOf(lines: string[], start: number, end: number): Layout {
  let contentStart = start;
  while (contentStart < end && lines[contentStart].trim() === "") contentStart++;
  const hasHeader =
    contentStart < end &&
    isTableRow(lines[contentStart]) &&
    contentStart + 1 < end &&
    isDivider(lines[contentStart + 1]);
  const dataStart = hasHeader ? contentStart + 2 : contentStart;
  let dataEnd = dataStart;
  while (dataEnd < end && isTableRow(lines[dataEnd])) dataEnd++;
  return { contentStart, hasHeader, dataStart, dataEnd };
}

function insertRow(lines: string[], section: Section, it: MediaItem): void {
  const [s, e] = sectionBounds(lines, section);

    lines.splice(lay.contentStart, 0, headerLine(), dividerLine(), rowToLine(it), "");
  } else {
    lines.splice(lay.dataEnd, 0, rowToLine(it));
  }
}

async function getJson(url: string, timeoutMs = 12000): Promise<unknown> {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), timeoutMs);
  try {
    const res = await fetch(url, { signal: ctrl.signal });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } finally {
    clearTimeout(timer);
  }
}

    .map((m) => ({

      name: asStr(m.name),
      year: firstYear(m.releaseInfo ?? m.year),
      poster: asStr(m.poster),
      kind,
      genres: asList(m.genres),
      imdbRating: asStr(m.imdbRating ?? ""),
    }));
}

    const m = data?.meta;

      kind,

      year: firstYear(m.releaseInfo ?? m.year),

      cast: asList(m.cast),
      description: asStr(m.description),
      runtime: asStr(m.runtime),
      country: asStr(m.country),
      status: asStr(m.status),

  }
}

15 · Practice

Break it on purpose: eight experiments

Reading builds the map; breaking builds the instinct. Each experiment is a tiny edit to the real code. Do it for real: open the file, make the change, run npm run dev, and predict the failure out loud before you trigger it. Then reveal the answer. Undo each experiment before starting the next.

1 · Remove the loop guard

In media.tsx, delete the line if (all.length === 0) return; (line 90).

What actually happens

Observed: with everything cached, the effect still fires detail() for every item on every run → thousands of requests, Raycast's CPU spikes, toasts may flood if any fail, the UI stutters.

Why: the effect's own setDescs re-arms it (descs is a dependency). The guard was the only thing that turned that loop into a countdown. Lesson: an effect that writes its own dependency needs an explicit fixed point.

2 · Replace the tokenizer with a naive split

In media-data.ts, change splitRow's body to return line.split("|").map(c => c.trim());, then load a list containing a rated movie (poster cell has !\|55) and edit any row.

What actually happens

Observed: every row gains two phantom cells (the poster's \|55 splits), so Type lands where Year should be, ratings drift into the wrong columns, and saving an edit permanently corrupts the file with shifted columns.

Why: the escaped pipe is data, not a delimiter. Only the peek-and-skip state machine knows the difference. Lesson: never split a format that has escapes; this is why CSV parsers exist. Restore from Git if you corrupted your real file, and notice you COULD, because it's plain text.

3 · Point the engine at a missing file

In media-data.ts, change NOTE_PATH to "/tmp/does-not-exist.md".

What actually happens

Observed: the list opens with a spinner, then a toast: "Couldn't read Movies.md, Not found: /tmp/does-not-exist.md". No crash, no stack trace in the user's face. Add Media still opens and its manual-add fails with its own toast.

Why: readLines throws → refresh's catch → failure toast → finally clears the spinner. Lesson: the throw-at-the-source / catch-at-the-view pipeline turns I/O failure into a one-line UX message. Every layer did exactly its job.

4 · Make one catalog failure kill the whole search

In cinemeta.ts, remove both .catch(() => [] as SearchHit[]) calls in searchAll, wrapping instead. Just delete them.

What actually happens

Observed: search normally works, until the Series catalog times out once. Then Promise.all rejects with that one error, the catch in add-media shows "Search failed", and the movie results that did arrive are thrown away too.

Why: Promise.all is fail-fast: first rejection wins, other branches' results are discarded. Lesson: per-branch .catch buys partial-success semantics: the difference between "the search is broken" and "series results are temporarily missing."

5 · Set the debounce to zero

In add-media.tsx, change the 320 timeout to 0.

What actually happens

Observed: typing "severance" fires nine searchAll calls (one per keystroke). Results flicker as tickets win and lose the seq race. It still works; the guard keeps state correct, but you've burned 9× the requests and the UI visibly churns.

Why: debounce controls VOLUME; the seq guard controls CORRECTNESS. They solve different problems (see §7.2). Lesson: removing one and keeping the other isolates exactly which problem each solves. That's the point of having both.

6 · Lose the checkbox override

In media-data.ts's markWatched, delete the watched: true, line from the insertRow object.

What actually happens

Observed: the row still MOVES to ## Watched, but its glyph stays ☐, and the list's Watched section shows an unchecked item. Worse: mark it "watched" again later and findRow("Watchlist") won't find it.

Why: {...hit.row, watched: true}: the override after the spread was the only thing forcing the destination's glyph. The row object being moved still says watched:false. Lesson: in spread-merges, order IS logic; a missing override isn't a type error, it's a silent data lie. The boolean and the section must be reconciled somewhere. Here, at insert time.

7 · Shrink the dependency array

In media.tsx's description effect, change the deps from [watchlist, watched, descs] to [watchlist, watched].

What actually happens

Observed: with >20 items, only the first 20 ever get descriptions; the rest stay plotless forever. With ≤20 items, nothing seems wrong at all.

Why: without descs as a dep, the effect never re-runs after the first batch lands. The re-arming IS the batch scheduler. Inside the async closure descs would also be a stale snapshot. Lesson: dep arrays aren't decoration; here the "missing" dep is the exact difference between "fetches everything in batches" and "fetches once."

8 · Delete the cancelled flag

In media.tsx, remove let cancelled = false;, the if (!cancelled) check, and the cleanup return and just call the async IIFE bare.

What actually happens

Observed: mostly nothing, until you close Raycast mid-fetch or a re-render overtakes a slow batch. Then: a state write to an unmounted view (React warning / wasted work), or an older batch's setDescs merging after a newer one. Nothing crashes dramatically, which is what makes this bug class insidious.

Why: the cleanup function is the effect's "last will": it marks in-flight work dead. Lesson: async work inside effects always outlives the render that started it; every effect that awaits needs either a cancellation flag, an AbortController, or a seq ticket. This codebase uses all three, one per context.
