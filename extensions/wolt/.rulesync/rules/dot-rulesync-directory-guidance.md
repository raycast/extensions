# Understanding the Agent-Rules Git Submodule

**CRITICAL**: The `.rulesync/` directory in this repository is a git submodule pointing to a shared `agent-rules` repository. This submodule contains centralized rules and commands that are maintained separately and shared across multiple projects. Understanding how to interact with it is essential for proper rule management.

## Core Principle

The `.rulesync/` directory is a **git submodule** that points to a centralized `agent-rules` repository ([https://github.com/OzTamir/agent-rules](https://github.com/OzTamir/agent-rules)). This allows the same set of rules to be shared across multiple projects without copying and pasting. Rulesync automatically discovers and uses rules from `.rulesync/rules/` and commands from `.rulesync/commands/` when generating tool-specific configurations.

## Repository Structure

In this repository, you'll find:

```
this-repo/
├── .rulesync/          # Git submodule → points to agent-rules repository
│   ├── rules/          # Shared rule files (read-only, maintained centrally)
│   ├── commands/       # Shared command files (read-only, maintained centrally)
│   └── mcp.json        # MCP server configuration (part of submodule)
├── .cursorrules        # Generated by Rulesync from .rulesync/rules/ (DO NOT EDIT)
├── CLAUDE.md           # Generated by Rulesync from .rulesync/rules/ (DO NOT EDIT)
└── ...                 # Other project files
```

## Understanding the Submodule

### What is `.rulesync/`?

The `.rulesync/` directory is a **git submodule** - a reference to a separate git repository (`agent-rules` at [https://github.com/OzTamir/agent-rules](https://github.com/OzTamir/agent-rules)). This means:

- The rules in `.rulesync/rules/` are **shared across multiple projects**
- Changes to rules in the `agent-rules` repository affect all projects using it
- The submodule points to a specific commit in the `agent-rules` repository
- You can read and reference these rules, but modifications should be rare and carefully considered

### How Rulesync Uses the Submodule

Rulesync automatically discovers and processes:

- **Rule files**: `.rulesync/rules/*.md` and `.rulesync/rules/*.mdc` - These define AI agent behavior
- **Command files**: `.rulesync/commands/*.md` - These provide reusable instruction templates
- **MCP configuration**: `.rulesync/mcp.json` - Model Context Protocol server settings

When `rulesync generate` runs in this repository, it:

1. Scans `.rulesync/rules/` for all rule files
2. Scans `.rulesync/commands/` for command files
3. Generates tool-specific files (`.cursorrules`, `CLAUDE.md`, etc.) in the repository root

### Important Distinctions

- **`.rulesync/rules/`**: Source rules from the shared repository - **READ AND USE THESE**
- **Generated files** (`.cursorrules`, `CLAUDE.md`): Auto-generated - **NEVER EDIT DIRECTLY**
- **Submodule nature**: Changes here affect other repositories - **MODIFY CAREFULLY**

## Required Workflow

### Primary Use: Reading and Using Rules

**Most of the time**, you should simply **read and follow** the rules in `.rulesync/rules/`. These rules are automatically included in your context when working on files that match their glob patterns.

1. **Rules are automatically active**: Rulesync has already generated `.cursorrules`, `CLAUDE.md`, etc. from `.rulesync/rules/`
2. **Reference rules when needed**: Check `.rulesync/rules/` to understand what guidelines apply
3. **Follow the rules**: The rules define how you should behave in this codebase

### Updating the Submodule Reference

When the `agent-rules` repository has been updated with new rules, update the submodule reference:

#### Method 1: Update to Latest (Recommended)

```bash
# From repository root
git submodule update --remote .rulesync
git add .rulesync
git commit -m "Update agent-rules submodule to latest"
```

#### Method 2: Manual Update

```bash
cd .rulesync
git pull origin main
cd ..
git add .rulesync
git commit -m "Update agent-rules submodule"
```

**After updating the submodule**, regenerate configurations:

```bash
rulesync generate --targets cursor,claudecode --features rules
```

**After generating**, update your `.gitignore` to exclude generated files:

```bash
rulesync gitignore
```

This automatically adds all Rulesync-generated files (like `.cursorrules`, `CLAUDE.md`, etc.) to your `.gitignore`, keeping your repository clean.

### Modifying Rules (Rare - Use with Caution)

**IMPORTANT**: Rules in `.rulesync/rules/` are **shared across multiple projects**. Modifying them here will affect other repositories using the same submodule. Only modify rules if:

1. The change should apply to **all projects** using these rules, OR
2. You're explicitly asked to update the shared ruleset

#### Workflow for Modifying Rules

1. **Navigate to submodule**:

   ```bash
   cd .rulesync
   ```

2. **Check current branch and status**:

   ```bash
   git status
   git branch
   ```

3. **Make changes** to rule files in `rules/` or command files in `commands/`

4. **Commit in submodule**:

   ```bash
   git add rules/your-rule.md
   git commit -m "Update rule: description of changes"
   git push origin main
   ```

5. **Return to parent repository** and update submodule reference:

   ```bash
   cd ..
   git add .rulesync
   git commit -m "Update agent-rules submodule"
   ```

6. **Regenerate configurations**:
   ```bash
   rulesync generate --targets cursor,claudecode --features rules
   ```

## Handling Submodule Conflicts

If you encounter conflicts with the submodule:

### Scenario: Submodule Points to Different Commit

If the submodule reference conflicts:

```bash
# Check what commit the submodule is pointing to
cd .rulesync
git log --oneline -5
cd ..

# Update to resolve conflict (usually update to latest)
git submodule update --remote .rulesync
git add .rulesync
git commit -m "Resolve submodule conflict: update to latest"
```

### Scenario: Local Changes in Submodule

If there are uncommitted changes in `.rulesync/`:

1. **Check what changed**:

   ```bash
   cd .rulesync
   git status
   git diff
   ```

2. **Decide**:

   - If changes should be kept: commit and push them
   - If changes should be discarded: `git checkout .` or `git reset --hard`

3. **Update submodule reference**:
   ```bash
   cd ..
   git add .rulesync
   git commit -m "Update submodule reference"
   ```

## Adding New Rules (Only if Shared Across Projects)

**CRITICAL**: Only add rules to `.rulesync/rules/` if they should apply to **all projects** using this submodule. For project-specific rules, use a different location (outside `.rulesync/`).

If you need to add a shared rule:

1. **Navigate to submodule**:

   ```bash
   cd .rulesync
   ```

2. **Create rule file** following the template in `.rulesync/commands/add-rule.md`:

   ```bash
   # Create file: rules/my-new-rule.md
   ```

3. **Use Rulesync MCP** (if available) or create file manually with proper frontmatter

4. **Commit in submodule**:

   ```bash
   git add rules/my-new-rule.md
   git commit -m "Add rule: description"
   git push origin main
   ```

5. **Update parent repository**:

   ```bash
   cd ..
   git add .rulesync
   git commit -m "Update agent-rules submodule"
   ```

6. **Regenerate configurations**:

   ```bash
   rulesync generate --targets cursor,claudecode --features rules
   ```

7. **Update `.gitignore`** (if needed):
   ```bash
   rulesync gitignore
   ```

## Examples of What NOT to Do

❌ **Don't**: Edit generated files like `.cursorrules` or `CLAUDE.md` directly - they're auto-generated from `.rulesync/rules/`
❌ **Don't**: Modify rules in `.rulesync/rules/` for project-specific needs - these rules are shared across projects
❌ **Don't**: Commit submodule changes without understanding they affect other repositories
❌ **Don't**: Skip running `rulesync generate` after updating the submodule
❌ **Don't**: Commit generated files (`.cursorrules`, `CLAUDE.md`) to git - use `rulesync gitignore` to exclude them
❌ **Don't**: Create project-specific rules in `.rulesync/rules/` - use a different location
❌ **Don't**: Modify `.rulesync/mcp.json` - it's part of the shared submodule
❌ **Don't**: Ignore submodule updates - keep it current to get latest rule improvements
❌ **Don't**: Make changes to `.rulesync/` without committing them properly in the submodule

## Examples of What TO Do

✅ **Do**: Read and follow rules from `.rulesync/rules/` - they're automatically active
✅ **Do**: Update the submodule reference when new rules are available: `git submodule update --remote .rulesync`
✅ **Do**: Run `rulesync generate` after updating the submodule to regenerate configurations
✅ **Do**: Run `rulesync gitignore` after generating to automatically exclude generated files from git
✅ **Do**: Check `.rulesync/rules/` to understand what guidelines apply to your work
✅ **Do**: Commit submodule reference updates in the parent repository after pulling changes
✅ **Do**: Use Rulesync MCP tools when available for reading rules programmatically
✅ **Do**: Follow the structure in `.rulesync/commands/add-rule.md` if you need to add shared rules
✅ **Do**: Understand that `.rulesync/` is a git submodule pointing to a shared repository
