## Input and result details

- Account IDs and draft IDs are numbers. Omitted `social_set_id` uses the saved default, or the sole available social set. Multiple accounts without a default cause an error. `list-social-sets` internally pages through the accounts and fetches their connected platforms. Only `set-default-social-set` writes the saved default. Authentication reads the extension's API Key preference, not CLI configuration.
- `get-social-set` returns the raw account detail. `get-current-user` returns raw user metadata. Neither implies that every post on a shared account was written by the requesting user.
- `list-drafts` accepts `status`, tag slugs, `limit`, `offset`, and `orderBy`. The API adapter maps `orderBy` to `order_by`; examples include `-published_at` and `-updated_at`. `all` omits the status filter. The tool returns a compact array and drops `count`, `next`, and effective page-size metadata. Titles/previews are normalized summaries, not complete text. Use `get-draft` for writing samples and edits. Offset pagination is possible, but incomplete samples do not prove an exhaustive history.
- `get-draft` returns the raw draft, including per-platform content, scratchpad, tags, scheduling and sharing data. `exclude_comment_markers` defaults to false. Marker-free output is for display, never an edit source. API fields present at runtime are not removed merely because the local TypeScript type omits them, including X Article content or publish-state metadata.
- `create-draft` requires final exact `content`. Omitted or empty `platforms` selects every connected supported post platform. Explicit choices are checked against the connected set. The supported keys are `x`, `linkedin`, `threads`, `bluesky`, and `mastodon`. Substack Notes is not included. Thread splitting requires a line containing exactly `---` between newlines; inline `---` does not split. LinkedIn merges those separators into paragraph breaks and remains a single post.
- `title` maps to internal `draft_title`; `scratchpad` maps to private `scratchpad_text`. Neither is published. `share: true` creates a public draft URL. Omit `schedule` on creation to save an unscheduled draft. On update, omitted metadata fields remain unchanged; supplied tags and scratchpad replace their previous values. `list-tags` internally pages through tags and returns slugs. `create-tag` requires its own requested change and tool confirmation.
- Each content-bearing `update-draft` rebuilds the supplied platforms' post arrays. Omitted `platforms` targets all currently enabled post platforms, potentially overwriting tailored copy. Other platform keys remain unchanged, as documented by `DraftUpdateRequest` in [api.json](../../api.json). The helper preserves target platform `settings`, such as X reply/community settings, but replacement does not automatically preserve the posts' media IDs, quote URLs, or disclosure labels.
- `media_ids` attaches only to the first post of newly supplied content. `quote_post_url` also applies only to the first X post. True `paid_partnership` and `made_with_ai` values apply to every X post. Existing first-post media/quote and uniform disclosures can be carried forward explicitly. There is no arbitrary array-of-posts input to preserve later-post media or quotes during a full text replacement. Per-post labels, alt text, thumbnails, and other fields lacking inputs cannot be rewritten faithfully through this interface.
- `append: true` preserves existing posts through `sanitizePost` and appends new ones. That sanitizer retains text, media IDs, and X quote/disclosure fields, but drops other per-post fields. Input `media_ids` applies to the first new post; a supplied `quote_post_url` applies to the first post of the combined X thread. Avoid quote changes during append unless that first-post behavior is intended. LinkedIn cannot append, and a platform must already have content before appending. For any edit, inspect the existing fields before assuming they can all be retained.
- X `reply_to_url` and `community_id` are creation-only tool inputs. Quote/disclosure options require X. False disclosure values and empty quote URLs do not clear existing values through the metadata-only update path. Replacing content can drop them, so use that path only when the intended full state is representable. `media_ids` alone does not produce an update without content.
- Post mutations return compact `draftResult` metadata, including `id`, `social_set_id`, status, title, preview, private/share URLs, scheduling/published dates, and tags. They do not return full posts, comment anchors, or all publishing-state fields. Read back with `get-draft`. There is no idempotency-key input; inspect uncertain outcomes before retrying creation or appending.
- `upload-media` takes an absolute local path, creates an upload, sends the file, and checks status up to 30 times with two-second waits. It can return `processing` with a `media_id`; recheck with `get-media-status` instead of creating another upload. Use an ID only after it is ready. Remote URL downloading and per-post placement are not supplied by these tools.
- `list-comments` accepts platform/status filters and offset pagination; its adapter defaults `limit` to 10. `create-comment` requires exact `selected_text` and comment `text`. Although optional in the type, `post_index` is required at runtime for ordinary posts; for `platform: "x_article"`, omit it or pass zero. `occurrence` identifies repeated selections. For the exact anchoring semantics, see the pinned upstream comments reference in [UPSTREAM.md](UPSTREAM.md).
- Comments can have span or self-closing paragraph anchors. Preserve both in content updates. `force_overwrite_comments: true` resolves comments whose markers are missing and is destructive. `resolve-comment` removes its anchor; `delete-comment` deletes one comment when `comment_id` is supplied, otherwise the entire thread. Tool confirmations cover resolution/deletion, but creation/replies/edits still require an explicit user request. None of these comment mutations is needed merely to apply feedback to copy.
- `resolve-linkedin-organization` takes a company/school URL and returns usable mention text. There is no corresponding person-mention resolver. Preserve existing mention syntax instead of inventing a URN or selecting only part of a mention when anchoring a comment.
- `schedule-draft.schedule_date` takes an ISO date-time with timezone or `next-free-slot`; it can lead to automatic publishing. `publish-draft` submits `publish_at: "now"`. The API describes publishing as asynchronous, so a submission is not proof of published status. `get-draft` can verify progress. The registered tool inputs have no nullable schedule field for unscheduling and no inert `plan` field. A string `"null"` is not a supported substitute.
- `get-queue` takes a date range; `get-queue-schedule` reads rules. `update-queue-schedule.rules` replaces all rules with hour/minute/day entries. `get-x-post-analytics` takes an inclusive date range and optional replies/offset pagination; `get-x-follower-analytics` allows omitted dates. These readers return raw API responses. Analytics tools cover X only, and performance does not establish authorship or the user's preferred voice.
- `create-x-article` and `update-x-article` use a standalone `x_article` payload. Supplied markdown must begin with `# ` after trimming. Article creation cannot mix with post platforms. Article update uses the literal string `"null"` only for removing `cover_media_id`, not for clearing a schedule. These tools are available for article requests but are outside this post/thread skill.
- The extension has no source-article fetcher, arbitrary post-body patch, native voice-profile reader/writer, style-lint tool, link-preview suppression input, Substack platform, or inert planning input. Unsupported operations stop rather than falling back to CLI, MCP, browser, filesystem, or invented tools.
