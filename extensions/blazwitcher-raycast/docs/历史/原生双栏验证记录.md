## 调试中修复的问题

1. **历史数据库锁**：Chrome 对 History 持独占锁，直接只读查询返回 `database is locked (5)`。后备方案改为私有稳定快照，包含 WAL/回滚日志，比较复制前后的文件指纹、检查 SQLite 完整性，读取完成清理，不修改源库。真实历史搜索与打开已成功。
2. **Raycast 内存不足**：完整历史命令曾显示 `Command Out of Memory`，注明 JS 堆上限 100 MB。原来的 2000 条记录缓存无法约束长 URL 的边界规模；现按边界和索引总单元数限额、避免重复保存组合原文，并对连续原文匹配直接走引擎等价的优先路径。修复后默认 20000 条历史和统一入口的搜索、刷新均通过。
3. **范围说明挤压结果标题**：缩短左侧区块说明，分别展示结果数量、所有窗口或历史读取上限；配置和来源保留在适合的位置。
4. **来源前缀与下拉框不一致**：下拉框显示实际来源；主动切换来源时保留关键词并清除旧前缀。

## 性能观察

修复前，20489 个候选的旧缓存方案堆内存采样约 129–146 MB；尽管普通 Node 进程能运行，真实 Raycast 已证明它会超过命令限制。

修复后一次普通 Node 本地测量如下，数据读取约 373 毫秒：

| 候选条数 | 索引时间 | zhongwen | zw     | github | 堆内存采样 |
| -------- | -------- | -------- | ------ | ------ | ---------- |
| 100      | 1 ms     | 3 ms     | <1 ms  | 1 ms   | 39–42 MB   |
| 1000     | 3 ms     | 33 ms    | 8 ms   | 22 ms  | 51–63 MB   |
| 20489    | 47 ms    | 456 ms   | 258 ms | 519 ms | 60–83 MB   |

同一实际数据在 64 MB old-space 限制下也能完成查询；更频繁的 GC 使三个大规模查询约为 1109/544/1017 毫秒，堆采样 39–51 MB。old-space 限制并不等于整个进程内存上限，也不等价于 Raycast 堆统计。

这些是本机 Node 的样本，不是 Raycast 端到端延迟或内存峰值保证。200 毫秒优化目标尚未全部达到。`npm run test:local` 可复测，只输出数量、耗时与内存统计。
