# FullForms List Raycast Extension. Project Context

## Overview

Raycast extension for the FullForms List glossary service (`list.fullforms.com`). Three commands ship: Search Entries (full-text search across every workspace the caller belongs to, with a markdown detail pane, starring, clipboard actions, and macOS TTS via `say`), Quick Add Entry (form-based entry creation on any list with edit access, with type-aware placeholders, a filterable tag picker, live duplicate detection, and a persistent "Last Added" banner), and Suggest Entry (queue an entry to a list owner's moderation queue when you only have view access). Bearer-token auth via `/api/v1/*` endpoints in the sibling `../list/` repo; the token is a Raycast password preference (Keychain-encrypted at rest), generated by the user at `list.fullforms.com/account`. No DB access, no service-role anything.

Brand: "List by FullForms" (the displayed title and store-listing branding). Published to the public Raycast Store as `raycast.com/mithunmathew/list-by-fullforms` (initial release 2026-06-12). Author handle is the personal `mithunmathew` account, not the `FullForms` org, because Raycast v1's publish flow auto-routes any `owner: "<org>"` to that org's private store (a Pro Teams paid-tier feature). See Common Pitfalls below for the full story; the workaround was to omit `owner` and let `author` carry the publishing identity.

## Dev workflow

```bash
npm install           # one-time. Pins react 19, @raycast/api 1.x, @raycast/utils 2.x.
npm run dev           # ray develop. Opens commands in Raycast v2 if running, falls back to v1.
npm run build         # ray build. Production bundle into dist/. Runs full TS check.
npm run lint          # ray lint. Validates manifest, runs ESLint + Prettier 3.8.3 over src/.
npm run fix-lint      # ray lint --fix. Auto-applies Prettier reformats. Run before any src/ commit.
npm run publish       # npx @raycast/api@latest publish. Re-syncs the raycast/extensions fork branch.
```

Token setup for dev. Generate a PAT at `list.fullforms.com/account` (or against a local list-repo dev server at `http://localhost:3000/account`), paste into Raycast > Extensions > List by FullForms > API Token preference. The optional API Base URL preference accepts a localhost override for iterating against a local list-repo dev server without rebuilding the extension.

The publish CLI is two-tier authenticated. First, `npx ray login` against the Raycast account (Raycast desktop app browser handshake); a personal-user context is required to publish public extensions. Verify which identity is active with `npx ray profile`. Second, the publish flow opens GitHub OAuth to fork `raycast/extensions` to your personal GitHub and push to a branch on that fork; the PR against `raycast/extensions:main` opens automatically.

## Architecture invariants

### Preferences are typed via the auto-generated `ExtensionPreferences` ambient

`src/lib/api.ts` reads preferences via `getPreferenceValues<ExtensionPreferences>()`. `ExtensionPreferences` is the ambient type Raycast auto-generates into `raycast-env.d.ts` from `package.json`'s `preferences` block, regenerated on every `ray build` and `ray develop`. **Never redeclare a local `Preferences` interface to pass instead.** A hand-written shape silently drifts from the manifest when a preference is renamed or added; the auto-generated one fails compilation at every call site the moment the field shape changes. This was Greptile's one P1 finding in the initial-release PR (raycast/extensions#28267) and the fix landed in commit d54b927 before human review.

### Wire shapes live in `src/lib/api.ts`, never re-declared

Every `/api/v1/*` response shape is exported from `api.ts` (`Workspace`, `Tag`, `ListRow`, `WorkspacesResponse`, `ListsResponse`, plus the per-command result shapes inside each `*.tsx` for fields not shared). Other modules import these; they never redeclare. Field shape mirrors what the server's `api_*_for_token` RPCs emit (camelCase where the server returns camelCase, snake_case where it returns snake_case). When the server widens a row (the list repo's migration 20260607000000 added `tags` to `/api/v1/lists`; 20260605000000 widened search rows with `tags`; 20260606000000 widened with `listIsPublic` + `workspaceType`), `api.ts` is the single update point.

**Defensive `Array.isArray` guards** wrap `selectedList.tags`, `entry.tags`, and similar even though the migrations guarantee the field. Reason: Raycast's `useFetch` with `keepPreviousData: true` keeps the previous response in memory across command launches, and the first paint after a server redeploy can briefly serve a cached pre-migration shape lacking the new field. Without the guard, the bare `.length` or `.map` crashes the whole command. The migrations make the field forward-safe; the guard makes the cross-deploy transition window forward-safe.

### `ApiError` carries status; command handlers branch on `error.status` and `error.message`

`apiFetch` in `api.ts` catches 401, 429, and 503 and re-throws with user-friendly copy ("Token invalid or revoked. Open extension preferences..."). Everything else surfaces as `ApiError(status, message)` where `message` is either the server's `statusMessage` (Nitro structured-error convention) or the raw response body. Command-side handlers switch on `error.status` for HTTP-level branching and `error.message` for structured RPC codes the server raises verbatim (`suggestions_not_enabled`, `list_not_accessible`, `limit_reached:entries (current=N, max=M)`).

Suggest Entry's `friendlySuggestionError` translates the structured codes into per-case toast copy. Other commands surface the raw message in the toast `message` slot.

### List icon and visibility catalog mirrors the web

`src/lib/listIconCatalog.ts` is a Raycast-vocabulary re-expression of the web's `app/utils/listIconCatalog.js` (icon glyphs + color palette) and `app/utils/listVisibility.js` (three-variant Public / Shared / Private chip resolver). The web is the source of truth. Keep this file and the two web files in lockstep when the catalog or variant set changes.

Three glyphs (`briefcase`, `food`, `sparkle`) don't have a 1:1 Raycast `Icon` enum value and use closest-fit substitutes (`Building`, `MugSteam`, `Stars`); the other 17 map directly. The fallback for an unknown or null glyph is `Icon.List`, matching `resolveListIcon`'s fallback in the web app. Colors are stored as hex strings (mirroring `COLOR_PALETTE.fg` in the web) rather than `Color` enum values because Raycast's `tintColor` accepts hex strings cleanly and no lossy mapping is needed.

### TTS subprocess lifecycle is three layers deep

The Search Entries TTS actions (`Cmd+T`, `Cmd+Shift+T`, `Cmd+Opt+T`) pipe through macOS's built-in `say` binary via `child_process.execFile`. The subprocess lifecycle is managed in `src/lib/tts.ts` with three independent shutdown layers because Raycast doesn't expose an official "view dismissed" lifecycle and Esc / Cmd+W / command-switch don't reliably traverse React's unmount path:

1. `useEffect` cleanup in the Search Entries command, fires on view unmount.
2. Module-level `process.on("exit", stopSpeaking)`, fires when Node terminates the extension process.
3. Module-level `process.on(signal, ...)` for `SIGTERM`, `SIGINT`, `SIGHUP`, each calling `stopSpeaking()` then `process.exit(0)`. The explicit exit is mandatory: installing a signal listener overrides Node's default-kill behaviour for that signal, and without the explicit re-exit the extension would refuse to terminate.

`execFile` (not `exec`) passes the speak text as a single argv slot so shell metacharacters in an entry's definition cannot be interpreted as command separators. `currentSay` is module-scope so two back-to-back speak invocations kill the prior playback (no overlapping audio). Stop uses SIGKILL (not the default SIGTERM) because `say` is sometimes slow to honor SIGTERM mid-utterance, and stop-feels-instant matters more than graceful shutdown of speech synthesis.

`composeSpeakable(term, definition, description)` joins fragments with Apple's TTS `[[slnc 400]]` directive (400ms silence). Rate is forced to 160 wpm via `-r 160` (default English voices ship at 175-200); glossary entries pack a lot of detail per sentence and the default rate runs past you.

### Optimistic update pattern via `useFetch.mutate`

The Search Entries star toggle uses `searchQuery.mutate(apiFetch(POST/DELETE), { optimisticUpdate: current => transformedRow })`. The optimistic shape flips synchronously; the mutate awaits the server response and rolls back on throw. The pattern is local to one action today, but the shape applies to any future toggle action (favorite, archive, etc.) and is worth re-using rather than open-coding.

### Auto-default-select first writable list

Both Quick Add Entry and Suggest Entry auto-select the first writable list once the lists fetch lands, via a `useEffect` watching `firstListId = writableByWorkspace[0]?.lists[0]?.id`. The dependency is the primitive id, not the array, so referential-equality re-fires don't fire. The convention is: workspaces RPC sorts personal-first then team-alphabetical, lists RPC sorts `updated_at DESC` within a workspace, so `buckets[0].lists[0]` is reliably "the user's most recently edited writable list inside their primary workspace" — the natural default.

### No em-dashes in user-visible copy

Per the standing FullForms style preference: no em-dashes anywhere user-visible, including UI strings, README and docs, commit messages, and chat responses. Use periods, commas, semicolons, colons, or arrows instead. Documented in `../fullforms-chrome/CLAUDE.md` as the canonical statement of the rule.

## Publishing flow

The path that worked, in order. Each numbered step has a "we hit this once" story preserved in the commit log of the initial release.

1. **Authenticate the Raycast CLI**: `npx ray login`. Opens a browser handshake against the Raycast desktop app's session. Verify a personal-user context (not org-scoped) via `npx ray profile`.

2. **Confirm `owner` is unset in `package.json`** (or set to the personal Raycast handle, not an org handle). The publish CLI inspects this field to pick public vs private store. There is no `--public` override flag.

3. **Confirm `name` is unique server-side**. Raycast keys server-side ownership on the manifest's `name` field. Once an extension has been published to any store under a name, subsequent publishes update that existing listing regardless of what the current manifest says about `owner`. Renaming the extension is the only path to break a prior server-side association short of asking support to delete the prior listing.

4. **Set `http.postBuffer` globally**: `git config --global http.postBuffer 524288000`. The publish CLI clones `raycast/extensions` into a temp directory and pushes from there; the buffer must be set at the global git config level. Setting it only on the personal-repo local config covers the personal push but not the publish CLI's fork push. The ~13MB metadata-PNGs push HTTP-400-disconnects without this.

5. **Capture metadata screenshots via Window Capture**. Assign a hotkey at Raycast > Settings > Advanced > Window Capture (conventional binding `Cmd+Shift+Opt+M`); the command is **not** in the root search. `npm run dev` must be running and the dev-mode green dot visible on the command for "Save to Metadata" to be enabled. Each screenshot lands at exactly 2000x1250 PNG into `metadata/<name>-<n>.png`. 3 to 6 screenshots required.

6. **Metadata filenames must match the extension `name`**. The Window Capture command names files from the `name` field at capture time. If the manifest is renamed after captures, the metadata folder has to be re-renamed to match (commit 23f0c56 is a reference for this rename), or the PR diff reads as a copy-paste mismatch.

7. **Run `npm run build` before publish**. Catches type errors and lint failures locally. The `ray lint` pipeline runs inside the publish flow too; a build failure aborts publish.

8. **Run `npm run publish`**. Forks `raycast/extensions` to your personal GitHub if not already forked, clones it to a temp dir, copies the extension into `extensions/<name>/`, commits, pushes to a branch on the fork (`ext/<name>`), and opens (or updates) a PR against `raycast/extensions:main`. The PR is initially Draft state with only the default template body.

9. **Edit the PR description manually**. Fill in the Description (what the extension does, what API it talks to), Screencast (drag 1 to N of the metadata PNGs directly into the editor; GitHub auto-uploads to `user-attachments/`), and the Checklist (tick each box). Then click "Ready for review" on the PR page.

10. **Greptile review fires automatically**. Findings are advisory (P1 / P2 / P3 internal severity, not Raycast blockers) but worth addressing before the human reviewer arrives. The Preferences-interface finding was the only one on the initial release; the fix landed pre-human-review.

11. **Re-publishing is idempotent at the PR layer**. `npm run publish` after the initial submit detects an open PR for this extension and updates the existing one rather than opening a second one. Useful for incorporating reviewer feedback: edit code locally, commit, `npm run publish` to re-sync.

## Common pitfalls

These come from the initial-release publish journey (raycast/extensions#28267, submitted 2026-05-23, merged 2026-06-12). Documented here so the next contributor doesn't repeat them.

### Raycast org handles are case-sensitive

`owner: "fullforms"` (lowercase) failed `ray lint` with a 404 against `/api/v1/organizations/fullforms`. The actual handle is `FullForms` with the original case preserved at creation, accessible as `raycast.com/FullForms`. URL slugs also preserve case (the lowercase `/fullforms` 308-redirects to `/FullForms`). The npm-scope / GitHub-username intuition that "platform handles are lowercase" does not apply.

### `owner` field routes to the org's private store

Setting `owner` to an organization handle the publishing user is a member of routes the publish to that org's **private** store (a Pro Teams paid-tier feature), bypassing the public PR flow entirely. There is no CLI flag to override this. The fix is to omit `owner` so the publish takes the public path under the personal `author` handle. The FullForms org's private listing at `raycast.com/FullForms/fullforms-list` exists as an artifact of this mistake during the initial release; it stays live until the Pro Teams plan is cancelled or support removes it.

### Server-side ownership persists across publishes

A name that landed in any store cannot be re-published to a different store without server-side deletion of the prior listing. Raycast support is the only path to that deletion, and the May 2026 v2 launch put `support@raycast.com` and `enterprise@raycast.com` into auto-reply mode directing all v1 inquiries to the v2 migration track, with no human responses available. The unblock was renaming the extension: `name: "fullforms-list"` to `name: "list-by-fullforms"` made the publish CLI see a fresh server-side name with no prior association, and the public PR flow took over (commit e8d5b5d).

### TypeScript + Raycast types alignment

Three TypeScript-version-specific things tripped the initial build pipeline:

1. **`skipLibCheck: true` is required in `tsconfig.json`**. Without it, the conditional type expression `Awaited<ReturnType<ReturnType<T>>>` in `@raycast/utils/dist/types.d.ts` (around the `UnwrapReturn` type, line ~25) trips TS2344 across every TS version we tested (5.4 through 5.9). The official `raycast/extensions` template ships `skipLibCheck: true`; align with that template's tsconfig generally.

2. **`@types/react` must match the version `@raycast/api` pins**. The package hard-pins a specific version (currently 19.0.10) as a regular dependency, not just a peer. If a different version is hoisted at the root, npm doesn't dedupe and TypeScript sees double declarations of every JSX intrinsic element, producing thousands of duplicate-identifier errors. Fix: pin `@types/react` exactly in `devDependencies` AND add an `overrides` block enforcing the same version (so transitive deps can't reintroduce a second copy).

3. **eslint v10 + `@raycast/eslint-config` v2 are required**. The v1 preset is legacy `.eslintrc.json`-style; v2 is flat-config-native (`eslint.config.mjs`). Match what the official `raycast/extensions` template ships, currently `eslint@^10.0.1` + `@raycast/eslint-config@^2.1.1`. Mismatched versions cause `defineConfig` from `"eslint/config"` to fail with `ERR_PACKAGE_PATH_NOT_EXPORTED` (that subpath only exists on ESLint v9+).

### `http.postBuffer` (twice)

The default 1MB HTTP buffer is too small for any push containing the metadata PNGs (~13MB total at 2.5MB each). Set it **globally** so both the personal-repo push AND the publish CLI's fork push inherit it. Setting it only on the local repo config covers the first push but not the publish flow's temp clone, which inherits from global git config only.

### Raycast v1 vs v2 (May 2026)

Raycast v2 launched 2026-05-14 as a separate macOS and Windows app, running alongside v1 (not a replacement; both coexist). v1 is officially in maintenance mode: no new features, no bug fixes; engineering is fully on v2. The extension API itself is continuously versioned via `@raycast/api` and `@raycast/utils`; the same npm packages target both desktop apps. `npm run dev` opens the extension in v2 if running, falls back to v1. So this repo does **not** need a "migrate to v2" step today; the extension is forward-compatible by virtue of using the current API package. Future breaking changes go through `npx ray migrate` codemods.

The v2 transition broke Raycast support's responsiveness for v1 inquiries (see the "Server-side ownership" pitfall above). Plan accordingly: account-management asks that need support intervention may not get human responses through the standard channels until v2 stabilizes.
