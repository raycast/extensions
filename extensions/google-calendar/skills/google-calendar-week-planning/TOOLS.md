## Input and result details

- Timed event inputs require RFC3339 timestamps with `Z` or numeric offsets. `duration` is minutes; all-day events use `allDay: true`, date-only `startDate`, and optional `durationDays`. Explicit all-day `endDate` is exclusive. Timed recurrence requires an IANA `timeZone`; recurrence is a newline-separated string of RFC5545 rules. Event-type constraints are enforced in `src/lib/events.ts`.
- Attendee fields accept comma-separated emails. `attendees` aliases required guests on event writes. Editing guest fields adds guests; an empty string clears that category. `recurrence`, reminders, and attachments replace their respective values. Event notification levels default to the extension preference.
- `suggest-time` accepts attendee or calendar emails and always includes the current user. Defaults are weekdays, 09:00–17:00, a 15-minute increment, no buffer, and 10 suggestions (maximum 50). `workDayEnd` must be later than `workDayStart`; overnight work windows are unsupported. Results contain `participants`, `searchedRange`, `workHours`, and `suggestions` with `start`, `end`, `displayStart`, `displayEnd`, and `timeZone`. Per-calendar free/busy errors throw; missing response entries are not separately checked by this tool.
- `check-availability` also includes the current user. `attendees` is required but may be an empty string for a solo check. Each result has `email`, `busyPeriods`, and `errors`; missing or errored results do not establish availability. Neither availability tool accepts a separate `calendarId` input.
- `search-events` defaults to future events, 10 per page, expanded recurring instances, and start-time ordering. Set explicit bounds for a week. `singleEvents: false` cannot be combined with `orderBy: "startTime"`. Primary-calendar birthdays are excluded unless `eventTypes` includes them; other filters still apply. `eventTypes` and extended-property filters accept comma/newline-separated strings. `list-event-instances` defaults to 50 results. Both accept up to 2500 and return `nextPageToken`.
- `list-calendars` defaults to 100 results in the implementation (its input comment says 10), with a maximum of 250. Calendar, settings, and ACL list pagination uses `pageToken` and returns `nextPageToken`. `get-calendar-settings` reads one setting when `setting` is supplied; otherwise it lists up to 100, maximum 250.
- Event results use `id`, `calendarId`, `htmlLink`, `start`, and `end`. Pass returned `id` as `eventId` for reads or mutations. Instance IDs target one occurrence; series IDs target the series. `move-event` changes calendars and the organizer, not the meeting time. Only default events can be moved. `import-event` requires an `iCalUID` and creates a private copy.
- `manage-calendar-labels` needs `name` for create/rename, `backgroundColor` for create/recolor, and `labelId` for rename/recolor/delete. Mutations require calendar owner access. `set-event-label` requires `labelId` for assign and at least `writerWithoutPrivateAccess` access; label IDs are calendar-specific.
- `manage-calendar` needs `summary` for create and `calendarId` for update/delete. Update/delete require ownership; the primary calendar cannot be deleted. `manage-calendar-list` always needs a `calendarId`; insert subscribes to an existing calendar, and remove only removes the subscription. Reminder and notification strings replace the full respective lists.
- `manage-calendar-sharing` needs `ruleId` for get/update/revoke, `scopeType` and `role` for grant, `scopeValue` for non-public grants, and `role` for update. `scopeType: "default"` grants public access and must omit `scopeValue`. Mutations require ownership; sharing notifications default to true.
